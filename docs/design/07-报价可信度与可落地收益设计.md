### 1.3 与 06 的关系

[06-制作收益历史设计](./06-制作收益历史设计.md) 已经定义了“制作收益历史”的展示层和 v2 口径：

3. **材料难度**：关键料是商店/采集/稀有/自产/硬缺口；

### 1.4 现有实现（`assets/profit.js`）

已在工作区实现的部分（与 06 v2 对齐）：

- `evaluate(itemId, point, tax)`：只认 `point.quotes`，无报价就走自造/缺价，不用 base 回填；
- `build()`：中间品无报价时递归自造，累加材料成本 + 精力；
- `history()` / `skillTop()` / `crossServer()`：历史收益、分技艺 Top10、跨服中位/P25–P75；
- UI：物价走势/区服趋势的“精力收益比”页签、材料链、`购买可落地/含自造` 状态。

仍缺的能力（07 的增量）：

1. **商店辅料未识别**：熟矾、黄蜡、绢带、竹沥、药曲等商店常驻无报价时，`build()` 会判“缺一线材料报价”，把归营旌、缝纫中间品等误杀；07 的 M1/M3 用 `vendor` 状态修正。
2. **只有 ok/not，没有 A/B/C**：没有流动性、持续性、纸面差、卡点解释；07 的 M2 补。
3. **没有精力上限/闲置**：`skillTop` 仍按 perE 排序；07 的 M4 补 3000E 限售组合与闲置提示。
4. **没有样本/时效**：`point.quotes` 只有价格，没有 `sample/at`；07 的 M1/M7 补 `quoteMeta`。
5. **只有 1 天历史**：`history()` 只能回放现有 13 个点；07 的 M7 补 30 快照。
6. **没有归因/异常**：价格跳变、目录修订、报价消失没有标记；07 的 M6 补。

> 因此 07 的代码策略是：**扩展 `profit.js`，不重写 `evaluate`**。`evaluate` 继续做“能不能算”；`landability.js` 在其上做“算出来的东西能不能落地”；`planner.js` 再做“能投多少精力”。

## 2. 设计原则

1. **不伪造**：无报价就是无报价。示例价、基准价、商店价、本服报价必须分栏/分状态，不静默混算。
2. **分层可信**：每个价格带来源和置信状态；每个收益带“可落地/薄市/纸面”标签。
3. **可解释**：A/B/C 不是黑盒分数，必须能展开“卡在哪、缺什么、差多少”。
4. **可执行**：perE 只是起点；最终给“能投多少精力、能卖多少件、剩多少精力”的组合。
5. **向后兼容**：旧页面、旧缓存、旧历史 JSON 不破坏；新能力以开关/附加列/新卡片渐进上线。
6. **数据最小侵入**：能预计算的不在端上重复算；能加可选字段的不改旧字段语义。

**排序理由**：

- 先做 M1/M2/M3：它们直接改变“这个配方能不能做”的决策；没有这三项，M4 的组合只是更精细的纸面排行。

- M5/M6 依赖 M1/M2 的数据，放二期；M5 的自产只进 B，默认开但不会进 A，严格视图可关。
- M7 是数据前提，可与 M1 并行；没有多日/版本标记，M6 的归因会把修订当行情。
- M8/M9 是展示与传播，放后；先把“本服可落地”做对，再谈分服榜和导出。

**最小可上线（1 个迭代）**：M1 来源状态 + M2 A/B/C + M3 硬缺口 + `/analysis` 三列（落地/可落地金精力/卡点）。不做自产、不做归因、不做多端。

## 5. 模块详细设计

### 5.1 M1 · 报价可信度中心（Quote Trust）

#### 回答的问题

> 这个物品在这个服，现在是本服实价、薄价、商店价、示例价，还是根本没价？

> 现状问题：`Store.price` 对所有非手动价格返回 `seed:true`，UI 统一标「示例」；真实拍卖报价与 base 回退无法区分。`Calc.stats` 的 `seed` 也把二者混在一起，所以“已校准 76%”并不等于“有 76% 实价”。

#### 输入

- `serverPrices[serverId][itemId]`：本服有效报价（价格）；
- `serverQuoteMeta[serverId][itemId]`：`sample`（样本数）、`at`（报价时间）、`source`（auction/filtered）；
- `itemAccess[itemId]`：`vendor/gather/craft/dungeon/treasure/planting/unknown`；
- `price-history`：该物品的报价持续时点、跨服覆盖、价格 CV。

#### 输出

```js
QuoteTrust.get(serverId, itemId) => {
  price: 188.7 | null,
  source: 'quote' | 'vendor' | 'base' | 'none',
  level: '实价' | '薄价' | '商店价' | '示例价' | '缺价',
  sample: 12 | null,
  quoteAt: '2026-11-20T23:07:14+08:00' | null,
  ageHours: 0.6 | null,
  coverageServers: 17,
  quotePersistence: 1.0,   // 30 个快照里有报价的比例
  priceCv: 0.022,
  confidence: 0-100,
  reasons: ['样本 12≥5', '2 小时内有报价', '17 服覆盖', 'CV 2.2%']
}
```

#### 状态判定（可解释，不做黑盒）

> 首版已接入手动/实价/商店/示例/缺价；**薄价（样本/时效）依赖 `serverQuoteMeta`，P1 补**。

| 状态 | 规则 | 参与计算 |
|---|---|---|
| **实价** | 本服报价 + `sample >= 5` + `age <= 6h` | 是，A/B 可落地 |
| **薄价** | 本服报价，但样本 <5 或报价 >6h | 是，但只能进 B，不能进 A |
| **商店价** | 无本服报价，但 `itemAccess.vendor = true` | 是，按目录/商店价，标“商店价” |
| **示例价** | 无本服报价，也不是商店，但有 `base` | 仅“兼容视图”参与，不参与可落地 |
| **缺价** | 以上都不满足 | 不参与，配方标记“缺价” |

> `confidence` 只做展示排序，不替代状态。权重建议：样本 35%、时效 25%、覆盖 20%、稳定性 20%；每一项在 tooltip 里列出来源，避免“分数黑盒”。

#### UI 落点

1. **/prices 价格库**
   - 新增“来源”列：`实价 / 薄价 / 商店价 / 示例价 / 缺价` 徽章；
   - 新增筛选：来源、样本不足、报价过期、无报价；
   - KPI 从“已校准/示例/缺价”改为“实价/薄价/商店/示例/缺价”；
   - 行展开：样本数、报价时间、17 服覆盖、30 快照持续性、用途数、卡住配方数；
   - 保留手动改价（改价后状态=`手动`，优先级最高）。

2. **/overview 总览**
   - KPI：“本服实价覆盖 202/267”；
   - 副文案：“薄价 13 · 商店 18 · 示例 34 · 缺价 0”；
   - 如果实价覆盖 <70%，显示一条“先去校准”提示，不阻塞页面。

3. **/analysis 分析页**
   - 新增“价格口径”切换：`可落地（实价+薄价+商店）` / `兼容（含示例）`；
   - 默认 `可落地`，首次切换弹一次说明；
   - 兼容视图保留旧数字，但标题加“含示例价，非落地收益”。

4. **/trends 走势**
   - 每个节点 tooltip 显示 `本服报价/基准价` + 样本/时效；
   - 报价消失的节点用空心点，不连线。

#### 验收

- [ ] 267 个物品在 17 服都能显示来源状态；
- [ ] `source='base'` 的物品在“可落地”视图被排除；
- [ ] 商店价不因“无拍卖报价”被判缺价；
- [ ] 玄元成品/地脉玄元/定魂丹砂在 /prices 一眼可见“示例/缺价”；
- [ ] 旧缓存/旧 JSON 不报错，缺 `quoteMeta` 时降级为“报价存在但样本未知”。

#### 依赖 / 风险

- 需要价格机器人保留 `sample` 和 `t`（现在被丢弃）；
- 历史补录没有 `sample`，只能按“报价存在/不存在”判实价/缺价，样本标“未知”；
- 商店清单需要 JX3BOX 来源 + 人工兜底，且要可版本化。

### 5.2 M2 · 可落地收益评级（Landability）

#### 回答的问题

> 这条配方现在能不能做？为什么不能？纸面收益和可落地收益差多少？

#### 输入

- 配方 `recipe`、区服 `serverId`、节点 `at`；
- `QuoteTrust` 的每个材料/产物状态；
- `MaterialAccess` 的硬缺口标记；
- 历史窗口的可行性、产物覆盖、报价持续性、价格 CV。

#### 输出

```js
Landability.grade(recipe, serverId, at) => {
  grade: 'A' | 'B' | 'C',
  feasible: true | false,
  paperPerEnergy: 48.3,
  strictPerEnergy: null,
  delta: null,
  blockedBy: [
    { itemId:'dimai', name:'地脉玄元', reason:'无报价且非商店/非自产' },
    { itemId:'xuan_yuan_shan', name:'玄元星平衫', reason:'成品无报价' }
  ],
  thinReasons: ['成品仅 6 服有报价', '价格 CV 28%'],
  quoteComplete: false,
  selfCraftUsed: false,
  energy: 200,
  profit: null,
  reasons: ['材料缺价', '成品缺价']
}
```

#### 评级规则

| 等级 | 规则 |
|---|---|
| **A 可落地** | 30 快照 ≥80% 可完整核算；成品 ≥8 服有报价且 ≥80% 时点有报价；成品价格 CV ≤25%；中位金/精力 >0；所有非商店材料为实价/薄价；**纯购买，不依赖自产** |
| **B 条件可落地** | ≥50% 时点可核算；成品 ≥4 服有报价；中位 >0；但流动性/稳定性不足，**或需要自产中间品（额外精力/多技艺）** |
| **C 纸面/不可落地** | 缺关键料、成品无报价、负收益、或仅靠示例价 |


> 评级是**配方级**，不是物品级。中间品配方也可能拿 A（如密银锭），但利润薄、价格在跌；UI 要标“中间品 A”，不要和成品 A 混在一起。
>
> **本服 vs 跨服**：本服视图（技艺/价格库/精力收益分析）不要求 `outCov`，A/B/C 由本服报价完整性、持续性、CV、收益决定；跨服视图（区服趋势/物价走势）才使用 `outCov >= 8/4`。不要把跨服覆盖写进技艺页。
>
> **口径开关**：`allowSelfCraft=true`（默认，与 `assets/profit.js` 一致）时，自产配方进 B；`allowSelfCraft=false`（严格视图，商店辅料仍按商店价）时进 C。审计报告的 27/21/106 是严格视图；默认视图以引擎输出为准，不把 27/21/106 当唯一真值。
>
> 历史不足 30 个快照时，用**可用快照数**做分母，并在 UI 标“样本不足”；首版可以用 13 个点 + 17 服覆盖，但不要用 30 当硬编码分母，也不要把“2.3 天”说成“30 天”。

#### 关键规则

1. **无报价的非商店材料** → C，不允许 base 回填；
2. **无报价的成品** → C，不允许“假设能卖”；
3. **商店常驻辅料** → 允许按商店/目录价，状态=`商店价`；
4. **自产中间品** → 默认进 B（条件可落地），不计入 A；严格视图关闭自产后降 C；grade 带 `selfCraft`、`requiredSkills`、`extraEnergy`；
5. **产物多配方** → 默认取区间末点严格收益最高的配方，固定整段，保证可比；UI 可切换；
6. **负收益** → C，不管报价多完整。

### 5.4 M4 · 可执行精力组合（Executable Planner）

#### 回答的问题

> 3000 精力怎么花？哪些配方能吃到精力？剩多少精力？旧贪心（无上限）和可执行（限售）差多少？

#### 输入

- A/B 池（M2）；
- 每配方精力、可落地利润；
- 成品覆盖/持续性（M1）；
- 限售上限（可配置）。

#### 限售规则（首版建议）

| 等级 | 成品覆盖 | 每日上限 |
|---|---|---:|
| A | ≥14 服 | 8 次 |
| A | 10–13 服 | 6 次 |
| A | 8–9 服 | 4 次 |
| B | ≥6 服 | 3 次 |
| B | 4–5 服 | 2 次 |
| C | — | 0 |

> 上限是**可解释的假设**，不是市场容量实测。UI 必须显示“上限来源”，并允许用户改。

#### 排序分数

不要只用当前 perE（会被单点尖峰带偏），建议：

```text
stablePerEnergy = sqrt(max(currentPerEnergy, 0) * max(medianPerEnergy, 0))
```

或更保守：

```text
stablePerEnergy = min(currentPerEnergy, medianPerEnergy)
```

首版用 `sqrt(current × median)`，并在 tooltip 显示当前/中位/差值；用户可切“当前优先/中位优先”。

#### 输出

```js

  profit: 39696,
  energyUsed: 2997,
  energyIdle: 3,
  allocations: [
    {recipeId, name, grade, count, energy, profit, cap, capReason}
  ],
  bySkill: {
    duanzao: {profit: 8410, energy: 910, idle: 2090},
    fengren: {profit: 25115, energy: 2845, idle: 155},
    ...
  },
  legacyGreedyProfit: 100748,   // 旧贪心/无上限，仅用于对比
  delta: -61052
}
```

   - 显示：利润、已用精力、闲置精力、参与配方数；
   - 表格：配方、等级、上限、次数、精力、利润、上限原因；
   - 底部：`旧贪心（无上限） vs 可执行（限售）` 对比条；

### 5.5 M5 · 垂直自产链（Vertical Craft）

#### 回答的问题

> 中间品没报价，我自己做划不划算？要多花多少精力？值不值？

#### 规则

- 对配方材料递归：
  - 有本服报价 → 买；
  - 无报价但商店 → 商店价；
  - 无报价但可自产 → 递归自产，累加材料成本 + 精力；
  - 无报价且不可自产 → 硬缺口，整链不可落地。
- 批量产出：按 `ceil(need / outputQty)` 计算批次；多余产出可：
  - 有报价 → 按报价抵扣（可选）；
  - 无报价 → 忽略（保守）。
- 循环检测 + 最大深度（当前 `assets/profit.js` 为 4；归营旌链深 3 足够，保持 4 即可，不贸然放宽）。
- 多技艺/等级要求：输出 `requiredSkills`、`requiredLevels`；没有玩家等级档案时，显示“需锻造/缝纫/烹饪/制药/梓匠 50”。

#### 输出

```js
VerticalCraft.calc(recipe, serverId, at) => {
  feasible: true,
  selfCraftUsed: true,
  totalEnergy: 600,
  totalCost: 5218,
  revenue: 33107,
  profit: 27889,
  perEnergy: 46.5,
  chain: [
    {item:'定营铁桩', qty:1, energy:120, cost:1207, source:'self'},
    ...
  ],
  requiredSkills: ['duanzao','fengren','pengren','zhiyao','zijiang'],
  requiredLevels: {duanzao:50, fengren:50, ...}
}
```

#### UI 落点

- 配方抽屉“自产链路”树：每个节点显示 `买/自产/商店/硬缺口`、数量、单价、精力、成本；
- “买 vs 自产”对比卡：总成本、总精力、perE、差价；
- 开关：“允许自产（会计入额外精力）”默认开（与 `assets/profit.js` 一致）；打开后自产只进 B，不进 A；严格视图可关；
- 打开后，A/B/C 评级带 `自产` 标签，不直接混入 A 榜；

- 自产链的精力机会成本没有计入（只计精力，不计“这些精力本来能做别的”），首版注明。

### 5.6 M6 · 收益归因与异常（Attribution）

#### 回答的问题

> 这个配方收益为什么涨/跌？是成品价、材料价，还是数据修订？

#### 规则

对两个节点 `t0 → t1` 的利润变化做分解：

```text
Δprofit = Δ(输出价 × 数量 × (1-税))
        - Σ Δ(材料价 × 数量)
        - Δ手续费
```

按贡献绝对值排序，输出瀑布图数据：

```js
Attribution.explain(recipeId, serverId, t0, t1) => {
  delta: -320,
  drivers: [
    {item:'五气归元丹', role:'output', delta:-260},
    {item:'药引', role:'material', delta:-45},
    {item:'甘草', role:'material', delta:-15},
  ],
  anomalies: [
    {at:'2026-11-19T08:54', type:'catalog_revision', note:'v3.3→v3.4，base 跳变'},
    {at:'2026-11-20T23:07', type:'price_spike', note:'成品 +49%'},
  ]
}
```

#### 异常类型

| 类型 | 规则 | UI |
|---|---|---|
| `price_spike` | 相邻节点涨跌 >30% 或 >3×CV | 橙色点 + tooltip |
| `quote_gap` | 报价消失/重现 | 空心点/断线 |
| `catalog_revision` | `catalogVersion` 变化或 `baseHash` 变化 | 顶部横幅“数据修订，不是行情” |
| `sample_drop` | 样本数骤降 >50% | 灰色标记 |
| `thin_quote` | 覆盖 <4 服 | 黄色带 |

#### UI 落点

- /trends “制作收益”页签（06 已有）增加：
  - “收益变化归因”瀑布图；
  - “异常节点”列表；
  - 节点 tooltip：报价来源、样本、时效、修订标记。
- /trends 顶部：`catalogVersion` 变化时显示一次性横幅，避免把修订当行情。
- 物品详情：价格线 + 报价持续性色带。

#### 验收

- [ ] 归因各项之和 ≈ 总 Δ（误差 <1 金）；
- [ ] v3.3→v3.6 的基准价跳变被标 `catalog_revision`，不标 `price_spike`；
- [ ] 定魂丹砂报价消失被标 `quote_gap`；
- [ ] 山水手绢 270→298 被标 `price_spike`；
- [ ] 异常不改变原始价格，只做标注。

#### 依赖 / 风险

- 历史太短（2.3 天）时，归因只能解释“日内/两日”，不能解释赛季；
- 多材料时瀑布图可能过长，首版只显示 Top 5 + “其他”；
- 税费/手续费变化要单独列，不与价格混淆。

## 6. 数据模型与兼容

### 6.1 `assets/data.js` 新增（可选字段）

```js
meta: {
  priceSchema: 2,
  quoteUpdatedAt: '...',
  serverQuoteMeta: {
    s_mengjiangnan: {
      fengwangjiang: { sample: 12, at: 1795010327, source: 'auction' }
    }
  },

```

**兼容**：

- `serverPrices` 保持 `serverId -> itemId -> price` 不变；
- 新字段缺失时，`QuoteTrust` 降级为“报价存在/不存在”，不阻塞；
- `itemAccess` 可单独放 `assets/access-data.js`，按需加载；首版建议放 `data.js`，减少请求。

### 6.2 `price-history` schema v2

```jsonc
{
  "schemaVersion": 2,
  "date": "2026-11-20",
  "catalogVersion": "v3.6",
  "catalogHash": "sha1:...",
  "base": {
    "at": "...",
    "prices": { "s_mengjiangnan": { "fengwangjiang": 188.7 } },
    "quoteMeta": { "s_mengjiangnan": { "fengwangjiang": { "sample": 12, "at": 1795010327 } } },
    "catalogPrices": { ... }
  },
  "samples": [
    {
      "at": "...",
      "prices": { ... },
      "quoteMeta": { ... },
      "catalogVersion": "v3.6",
      "catalogHash": "sha1:..."
    }
  ]
}
```

**兼容**：

- 旧 `schemaVersion:1` 文件继续可读；`quoteMeta` 缺失时 `sample=null`；
- `prices` 语义不变（只存有效报价）；
- `catalogPrices` 语义不变（基准价）；
- 新字段只增不改。

### 6.3 设置

```js
settings: {
  pricePolicy: 'vendor' | 'compat',   // 默认 vendor（推荐）；旧用户首次提示
  showPaper: false,
  allowSelfCraft: false,
  energyPlan: 'standard' | 'conservative' | 'aggressive',
  caps: { A8: 8, A6: 6, A4: 4, B3: 3, B2: 2 },
  playerLevels: { duanzao: 50, ... } // 可选，用于自产链/归营旌
}
```

**迁移**：

- 旧缓存没有 `pricePolicy` → 默认 `'compat'`，但 /analysis 首次进入提示“建议切到可落地口径”；
- 用户手动切到 `'vendor'` 后记住；
- 不强制改变旧页面数字，避免“打开就变”。

### 6.4 构建期审计数据

`scripts/build-audit-data.mjs` 输出：

- `assets/audit-data.js`（Web，可选加载）：当前快照 154 配方 × 17 服的 grade/blockedBy/perE；

## 10. 风险与边界

| 风险 | 影响 | 对策 |
|---|---|---|
| 报价≠成交量 | A/B 仍可能卖不掉 | 文案常驻；限售上限；不承诺收益 |
| 样本只有 2.3 天 | 趋势/持续性弱 | 标“样本不足”；历史补录；不 extrapolate 赛季 |
| 商店清单误判 | 把硬缺口当商店，虚增可落地 | 人工覆盖表 + 版本化 + 审计页可查 |
| 目录版本跳变 | 把修订当行情 | `catalogVersion`/`catalogHash` 标记；异常分类 |
| 默认口径改变 | 老用户数字突变 | 默认兼容；新视图默认可落地；首次提示 |
| 自产链跨 5 技艺 | 大部分玩家不可用 | 默认关闭；明确“全 50”假设；显示所需技艺 |
| 小程序包体积 | 审核/加载 | 只带摘要；按需加载；压缩 |
| 数据量增长 | 仓库/构建变慢 | 按日归档；compact；只补录一次 |
| 评级阈值硬编码 | 赛季变化失效 | 配置化；版本号；审计页展示阈值 |

**本轮不做**：

- 成交量/需求预测；
- 跨服倒卖/套利建议；
- 自动改价/自动上架；
- 五行石概率收益（单独模型）；
- 玩家角色/装备扫描。
